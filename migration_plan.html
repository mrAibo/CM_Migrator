Migrations-Projektplan: IBM Content Manager (DB2 nach Oracle)

1. Management Summary

Dieser Plan beschreibt die Strategie zur Migration von ca. 20 Millionen Dokumenten (Items) aus einem IBM Content Manager (Source: DB2) in einen neuen IBM Content Manager (Target: Oracle). Das Ziel ist eine hochperformante, unterbrechungsfreie (resumable) und nachweislich verlustfreie Migration.

Kern-Features der Lösung:

  • Journaling: Persistente Statusverfolgung in einer lokalen Embedded-Datenbank (H2). Ermöglicht Neustarts ohne Wiederholung bereits migrierter Daten.
  • Performance: Multi-Threaded Producer-Consumer Architektur mit Streaming-Technologie und Connection Pooling.
  • Integrität: On-the-fly Checksummen-Validierung (SHA-256) und lückenloses Audit-Log.

2.2 Technologie-Stack

  • Sprache: Java 11+ (IBM CM Java APIs: DKDatastoreICM, DKLobICM, DKDatastorePool).
  • Datenbank (Journal): H2 Database (Embedded, File-based) – Schnell, SQL-fähig.
  • Logging: Log4j2 (Asynchrones Logging für Performance).
  • Build: Maven.

3. Detaillierte Migrations-Strategie

3.1 Journaling (Die "Resumability"-Engine)

Um sicherzustellen, dass bei einem Abbruch nicht von vorne begonnen werden muss, wird jeder Item-Status protokolliert.

Datenbank-Schema (Tabelle MIGRATION_JOURNAL):

Spalte Typ Beschreibung
SOURCE_PID VARCHAR(100) Primärschlüssel (Item ID der Quelle)
TARGET_PID VARCHAR(100) Item ID im Zielsystem (nach Erstellung)
STATUS VARCHAR(20) PENDING, IN_PROGRESS, COMPLETED, FAILED
CHECKSUM VARCHAR(64) SHA-256 Hash des Inhalts (zur Verifikation)
ATTEMPTS INT Anzahl der Versuche (für Retry-Logik)
ERROR_MSG TEXT Letzte Fehlermeldung (falls FAILED)
UPDATED_AT TIMESTAMP Zeitstempel der letzten Änderung

3.2 Performance-Optimierung (Update)

Bei 20 Mio. Objekten ist I/O und Latenz der Flaschenhals.

  1. Connection Pooling (DKDatastorePool):
    • Wir nutzen die eingebaute com.ibm.mm.sdk.common.DKDatastorePool Klasse.
    • Verhindert teuren Login-Overhead pro Item. Jeder Worker leiht sich eine Verbindung.
  2. Bulk Retrieval (retrieveObjects):
    • Der Reader nutzt DKDatastoreICM.retrieveObjects(dkCollection, options) um Metadaten für 50-100 Items in einem Roundtrip zu laden.
    • Dies ist signifikant schneller als Einzel-Abfragen.
  3. Streaming Add (DKLobICM.add):
    • Nutzung von DKLobICM.add(InputStream, length) für direkten Stream zum Server ohne Zwischenspeichern im RAM/Disk.
  4. Text-Index Deaktivierung:
    • Empfehlung: Text Search Indexierung auf dem Zielsystem während der Migration deaktivieren (oder auf "Scheduled" setzen), um Insert-Performance zu maximieren.

3.3 Daten-Integrität & Nachweisbarkeit

Der Kunde fordert "nachweislich ohne Verlust".

  1. On-the-fly Hashing:
    • Nutzung von DigestInputStream (SHA-256) während des Streams.
    • Vergleich mit sourceItem.getMD5Hash() (falls im Quellsystem vorhanden) als Zusatz-Check.
  2. Metadaten-Erhalt:
    • Explizites Setzen von setMimeType(), setOrgFileName() und setSemanticType() auf dem Ziel-Objekt, um 1:1 Kopien zu garantieren.
  3. Audit-Report:
    • Abschluss-Report aus der H2-DB (Erfolgsquote, Liste der Fehler).

4. Implementierungs-Phasen

Phase 1: Setup & Proof of Concept (PoC)

  • Einrichten der DKDatastorePool Konfiguration.
  • Implementierung des H2-Journals.
  • PoC: Migration von 100 Dokumenten mit Checksummen-Validierung.

Phase 2: Core Development

  • Implementierung FastBatchItemMigrator mit retrieveObjects Optimierung.
  • Implementierung der Streaming-Logik mit DigestInputStream.
  • Handling von MimeType und OrgFileName.

Phase 3: Testing & Tuning

  • Lasttest mit 100.000 Dokumenten.
  • Tuning der Pool-Größe (process.writer.threads).

Phase 4: Go-Live

  • Initiale Vollsicherung.
  • Start der Migration.

5. Beispiel-Code (Optimiert)

// Initialisierung des Pools (einmalig)
DKDatastorePool pool = new DKDatastorePool(new DKDatastoreICM());
pool.setDatastoreName("TargetServer");
pool.setMinAndMaxPoolSize(5, 20);

// Worker Logic
public void run() {
    dkDatastore ds = null;
    try {
        ds = pool.getConnection("user", "password");
        DKDatastoreICM dsICM = (DKDatastoreICM) ds;
        
        // ... Journal Update ...

        // Source Item (bereits via retrieveObjects geladen)
        DKLobICM sourceLob = (DKLobICM) sourceItem;
        
        // Target Item erstellen
        DKLobICM targetLob = (DKLobICM) dsICM.createDDO("MyTargetType", DKConstant.DK_CM_DOCUMENT);
        targetLob.setMimeType(sourceLob.getMimeType());
        targetLob.setOrgFileName(sourceLob.getOrgFileName());
        
        // Stream & Hash
        try (InputStream is = sourceLob.getInputStream(options);
             DigestInputStream dis = new DigestInputStream(is, MessageDigest.getInstance("SHA-256"))) {
             
            targetLob.add(dis, sourceLob.getSize()); // Streaming Add
            
            String checksum = Hex.encodeHexString(dis.getMessageDigest().digest());
            // ... Journal Commit ...
        }

    } finally {
        if (ds != null) pool.returnConnection(ds);
    }
}
